## SQLite 迁移演练

先让任务完成或明确取消并处理至终态，再停止后端。以下命令在项目根目录执行，使用项目 Python 环境。不要对正在运行的实例执行维护命令。命令不会自动终止任务，也不会修改实际现存库，除非显式指向它。

```powershell
python -m backend.manage --database backend/data/tasks.db --media backend/media backup backups/pre-v4
python -m backend.manage --database staging/tasks.db --media staging/media restore backups/pre-v4
python -m backend.manage --database staging/tasks.db migrate
python -m backend.manage --database staging/tasks.db init-admin --username admin
python -m backend.manage --database staging/tasks.db --media staging/media validate
```

备份记录原媒体根目录；恢复时会将 files、jobs 的输入/输出/Mask 路径及任务规则中位于该根目录内的路径改为新媒体目录。跨操作系统迁移建议保持容器内 `/app/backend/media` 路径，根目录之外的引用须单独处理。校验命令返回缺失文件清单，出现缺失时不可上线。

恢复命令拒绝覆盖已有数据库与媒体。备份包括敏感渠道配置，应限制备份目录权限。发生真实充值后，不能直接恢复旧库抹掉账目。

## PostgreSQL

安装更新后的 `backend/requirements.txt`，设置强随机 `POSTGRES_PASSWORD`（URI 特殊字符须编码），使用：

```powershell
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d postgres
```

停止后端的状态下，在 backend 容器中运行维护命令（首次可用 `docker compose ... run --rm backend python -m backend.manage ...`）。空库执行 `migrate`、`init-admin`；导入历史库执行 `import-sqlite /app/backend/data/tasks.db`，源 SQLite 必须已在演练副本上完成迁移及超管初始化。导入目标必须为空或与源库内容完全相同。之后执行 `validate`，确认后启动单个后端进程。不要先启动后端再导入，以免自动播种渠道造成冲突。

PostgreSQL 使用 `pg_dump` / `pg_restore`，媒体另行备份。生产 HTTPS 设置 `COOKIE_SECURE=true`，并配置准确的 `FRONTEND_ORIGINS`。

## P1 账号与隔离

迁移 3 新增验证码与登录限流记录，以及按所有者唯一的分类显示名称。注册用户名统一为 3–24 位中文、字母、数字、下划线，不能为纯数字；密码 8–64 位。手机号暂支持中国大陆号码。

- `/api/auth/sms` 支持 `register`、`reset` 两种用途，验证码 5 分钟有效、最多 5 次验证、单次使用；同一手机号发送间隔 60 秒、每天最多 10 次，同一来源 IP 每小时最多 20 次。密码登录按账号和来源分别限流。不会信任客户端提供的代理 IP 头。
- 验证码摘要使用数据库中的随机 HMAC 密钥，原码不存数据库、不返回 API、不写日志。重置密码撤销全部旧会话；禁用后撤销会话，重新启用不恢复旧会话。
- 任务详情、取消、下载、源图、输出文件名、Mask、缩略图、OCR、拼接及模板分类均校验归属；批量引用先逐项检查再操作。普通用户无法访问渠道、用户管理及未计费生图/重试入口；私有资源越权返回 404。
- 普通用户首页统计仅自己的任务，渠道与平台预估成本不展示；任务/OCR 错误不暴露内部路径和上游原始错误。公共模板只由管理员发布，用户可以读取公共模板并维护自己的私有模板。
- 新增 `/register`、`/forgot-password`；登录页面支持用户名/手机号，登录守卫与角色导航生效。普通用户可上传、识别、拼接、维护模板；P2 已开放积分生图。
- 管理员 `GET /api/admin/users` 与 `POST /api/admin/users/{id}/status` 支持用户启停，要求原因并写审计。当前尚无用户管理页面。

### 短信配置

默认 `SMS_MODE=disabled`，发送返回明确的 503。真实服务通过 `SMS_MODE=http`、`SMS_HTTP_URL`（HTTPS）、`SMS_HTTP_TOKEN` 对接自有服务商网关：POST JSON `phone/purpose/code/request_id`，接收成功返回 HTTP 200 和 `{"accepted":true}`。不自动重试发送；当前未配置或验收真实供应商。

本地开发可设置 `APP_ENV=development`、`SMS_MODE=test`、`SMS_TEST_OUTBOX=绝对路径`，验证码写入该目录的独立 JSON 文件。收件目录必须与媒体目录分离，不能公开映射；生产环境不接受测试发送模式。浏览器通过正常注册流程发送后，开发者在本地收件目录查看验证码。

## P2 积分账本与生图结算

迁移 4 增加积分账户、来源批次、只追加流水、手机号领取凭证、任务冻结轮次、幂等业务请求和实际调用记录。流水通过数据库触发器禁止修改与删除。现有账号初始化为零余额，历史任务不补扣，不给升级前账号自动补发体验积分。

- 注册与领取 3 积分在同一事务内完成，7 天有效，手机号唯一领取。按最早到期批次优先冻结，付费批次支持永久有效；查询和结算时处理到期。被冻结的体验积分可跨期完成原任务，过期后失败释放同时记过期流水，不回到可用余额。
- 普通用户多图、参考图组合和多比例入口按每张最终图片 1 积分计费。预览由后端计算张数与所需积分；创建任务、冻结和幂等凭证原子提交后才调度。余额不足返回 402；重复幂等请求返回原任务，改变参数复用凭证返回 409。
- 成功状态与单图扣费同事务提交；自动重试保留原冻结，终态失败或取消释放。手动重试仅选择失败或取消的图片，创建新冻结轮次；取消后晚到响应不扣费。并行步骤异常时等待同批在途步骤结束再终结任务。
- 启动时恢复已落库待执行任务，核对成功未扣费和终态未释放；输出采用临时文件原子替换，最终处理后写完成回执，补偿文件已完成但数据库尚未提交的窗口。回执带执行轮次，旧轮次结果不能结算新重试。原始输出完成到最终处理及回执写入之间的进程退出仍可能重新请求上游；没有可信成本来源的调用记为未知，不作为实际账单。
- 普通用户跨任务合计默认 1 张并发；会员额度与公平调度见 P3。旧版单图、批量及高级编辑仅超管可用，普通用户仅开放 OCR 识别，不开放额外生图编辑。
- 工作台显示积分余额和最终图片数，任务详情展示扣费、冻结与释放数量；`/account/credits` 展示来源批次、有效期与分页流水。充值入口尚未实现，页面明确说明。

继续使用单后端进程；SQLite 使用立即事务，PostgreSQL 积分事务使用数据库事务级锁，避免并发超扣。维护 `validate` 增加账户、批次和流水余额核对，SQLite → PostgreSQL 导入包含新增账本表。

本阶段含 SQLite 与 PostgreSQL 的全量测试 69 项通过，前端 TypeScript 与 Vite 生产构建通过。浏览器使用独立临时数据库、媒体目录和模拟生图服务验证：预览两张需 2 分，成功后 3 分变 1 分、冻结归零，积分页明细正确；重复提交返回原任务，余额不足返回 402。没有调用真实生图上游，也未修改实际在用数据库与媒体。自动测试覆盖并发冻结、幂等、部分成功、自动及手动重试、取消晚到、跨期释放、完成回执恢复、注册失败回滚和并行异常结算。

## P3 套餐、会员与额度

迁移 5 新增套餐及会员权益流水。四个建议套餐（6 元/30 分、18 元/120 分、12 元/100 分/7 天、36 元/360 分/30 天）全部初始化为草稿，不默认公开或出售。管理员在 `/admin/packages` 新建、编辑、上架、下架和排序；价格使用整数分，天数与套餐类型在接口及数据库校验，变更记录审计。历史套餐不物理删除，下架保留引用。公开 `GET /api/packages` 只显示上架套餐。导入工具复制套餐及会员流水，并用源库套餐替换目标库未经编辑的建议草稿。

- 会员按 UTC 到期时间动态判定；续期服务在调用方的积分事务锁内执行 `max(now, expires_at) + days`，业务凭证唯一，重复调用不重复续期，参数改变返回冲突。积分包发积分不触碰会员到期日，付费批次永久有效。该服务供 P4 核实入账事务组合使用，当前不提供模拟收款或直接开会员入口。
- `USER_CONCURRENCY=1`、`MEMBER_CONCURRENCY=3` 可配置，要求 `1 <= 普通 <= 会员 <= 20`。用户额度跨任务、跨渠道合计；同时保留每渠道共享并发。调度同时获取用户与渠道空位，繁忙渠道等待不提前占用户额度；在可启动的不同用户间轮转，避免同用户排队占满机会。调度每 50ms 检查一次，适用于当前单进程小范围使用。
- 每次上游请求（含重试）启动前重新判断会员到期，已在途请求不受随后到期影响。用户禁用与取消仍在实际请求开始前校验。内部未计费管理员调用不受用户额度约束，仍遵守渠道容量。
- `/account/membership` 显示会员状态、到期时间、可用积分、并发额度和已上架套餐，分别说明积分包及会员卡。人工充值购买流程见 P4。

## P4 人工充值订单与审核入账

迁移 6 新增收款资源、不可变收款码版本、订单快照、付款信息修订历史、收款核销、审核记录、财务幂等凭证及积分调整记录。套餐和收款码缺一不可创建订单；创建幂等请求保存名称、金额分、积分、会员天数与收款码版本。修改套餐、下架及替换收款码均不改变旧单。

- 用户 `/orders` 查看本人订单，详情显示原收款码和付款说明，提交交易号、带时区付款时间及可选截图，可多次补充并保留历史。提交只转待审核，不发积分。仅待付款且未提交材料的本人订单可取消。已取消且实际已付，由管理员专门补录核实，必须填写说明。
- `/admin/payment-settings` 上传新收款码版本（默认停用），明确启用时停用原版本，启停必须填写原因并写审计。旧图片与说明持续为原订单保留，不提供覆盖旧版本接口。同一时间最多一个启用版本。
- `/admin/orders` 按状态分页查看审核队列，订单详情要求管理员核实实际收款渠道、金额和交易号，或填写需补充材料原因。用户申报号与管理员核实号分开。核实金额必须等于订单快照；同收款渠道交易号数据库唯一，不能核销多单；同单重复核实返回原结果，不重复发积分或续期。
- 核实收款、永久付费积分批次及流水、会员续期、订单状态、审计和幂等凭证在一个事务内完成。当前 SQLite 立即事务、PostgreSQL 财务公共事务锁在读取订单前取得，串行化核实与账户变更；发放途中异常完整回滚。
- `POST /api/admin/users/{id}/credit-adjustments` 支持带原因及幂等键的正负积分调整，独立记录，不生成收款订单。负调整只扣可用积分，保留冻结、不允许透支；正调整永久有效。用户管理调整页面留待 P5。
- 付款图片保存在独立 `payment_assets` 表与媒体 payments 子目录，不进入普通文件命名空间；专用读取仅本人和超管，收款码仅对应订单本人和超管。禁止普通生图、OCR、拼接、模板引用；响应 private/no-store。图片限制 10MB、2500 万像素，验证后转 PNG 去除元信息。备份包含这些图片，恢复重定位资源路径，验证与 SQLite→PostgreSQL 导入均包含新增记录。
- 前端提交创建、材料、取消和审核使用幂等键，网络响应不明时保留凭证，变更参数生成新键。顶部导航增加订单、审核、收款设置，拥挤时支持横向滚动。
