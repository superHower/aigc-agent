# v4 发布与运营

代码已包含 P0–P5 的主要业务能力；真实服务验收仍需操作者完成。当前不宣称已接通真实短信或实际收款，不自动发布、迁移在用数据库或更改既有套餐价格。

## 发布步骤

1. 在演练环境安装依赖、使用 PostgreSQL，执行 `python -m backend.manage migrate`；首次执行 `python -m backend.manage init-admin --username 管理员名称`，在终端输入密码。无默认密码。沿用已有库时先停止接新任务，等待或明确取消在途任务，停止后端后备份数据库与全部媒体。
2. SQLite 使用维护工具 backup/restore 演练到新目录；PostgreSQL 使用 pg_dump/pg_restore 并单独备份媒体。演练副本执行 migrate、init-admin、validate，再按实施记录导入 PostgreSQL 并校验。实际发生充值后禁止恢复旧库抹掉账目。
3. 配置 HTTPS 与 `COOKIE_SECURE=true`、准确的 `FRONTEND_ORIGINS`、生产 PostgreSQL 凭据和独立媒体目录。数据库会话与短信 HMAC 密钥须随数据库备份，不能公开媒体目录。只启动一个后端执行进程，不使用多 worker 或多副本。
4. 配置 `APP_ENV=production`、`SMS_MODE=http`、HTTPS 服务商网关与令牌，按实施记录网关契约实测真实手机号：注册、错误码、超时、重复发送限制、验证码用途隔离和找回密码。测试收件模式不可用于生产；接口不返回原始验证码。令牌不写入截图或工单。
5. 管理员确认套餐价格后上架，在收款设置上传真实收款码、核对收款人及说明，启用正确版本。未配置有效码不允许新建订单。更换图片产生新版本，原订单继续查看原版本。
6. 使用两个测试用户验证登录隔离、无余额拒绝、生成成功扣一次、取消/最终失败释放、套餐订单和材料补充；进行一笔经操作者授权的小额真实付款，在收款账户核对后人工入账，再核对交易号、积分流水和会员时长。截图不能作为自动入账依据。
7. 经营总览查看配置状态。配置检查只是提示，不代表真实短信、HTTPS、实际收款和恢复演练验收通过。完成外部验收后再开放小范围用户。

## 日常操作

- 充值审核：只在收款账户确认实际到账后填写核实交易号与金额。不能匹配时要求补充材料，填写原因。已取消而实际付款走取消后补录，保留审计；同渠道同交易号只能核销一单。
- 用户管理：禁用撤销已有会话，停止后续生成请求，在途请求继续完成账务。补偿使用积分调整，正负调整均须原因与幂等凭证，不能伪造成收款。负调整不扣冻结、不透支。
- 公共模板：提示词管理由管理员设置公共范围，分类与模板范围须匹配。普通用户不能编辑公共模板。
- 渠道管理：单次请求估算成本以整数分配置，可留空。估算包含已调用 SDK 的失败及重试，不等于实际账单。没有可信成本来源时显示未知；SDK 调用记录不能证明上游已经接收请求。
- 经营统计：充值按核实入账时间，积分按结算流水发生时间，任务按创建时间。余额、待审核和禁用用户数为当前快照；日期按选择日期对应的浏览器 UTC 偏移聚合，跨夏令时切换的周期采用同一个偏移。
- 故障追踪：订单 ID 查审计，图片 job ID 查调用明细，区分逻辑图与每次请求、重试、渠道/模型快照及取消晚响应。不要向普通用户提供上游原始错误、密钥或内部路径。

## 故障恢复与限制

单进程启动会恢复已落库任务、核对积分冻结和最终输出回执。最终输出处理前后的窗口和上游响应丢失仍可能产生重复调用/未知成本；不要假定超时就未收费。保留数据库、媒体 output/receipts/snapshots/payments 目录及备份。

出现账务疑问时先停止接新订单与任务，保存当前数据库和媒体，核对实际收款与流水，完成账本验证；不要删除或改写历史流水。发布回退需要兼容新增账表，真实充值后不得直接覆盖旧库。

本地验证使用独立数据库/schema、媒体和端口；不对实际在用数据执行测试。当前审计界面仅管理员可见；短信凭据、密码与渠道密钥不进入审计摘要。订单与付款图日常不物理删除。上传中断的未引用付款图需在停止服务、备份后人工核对处理，目前无自动清理任务。
