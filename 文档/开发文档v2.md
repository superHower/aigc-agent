二、Mask 的 Alpha 语义统一
确认结果：官方语义是“透明区域 = 要编辑的区域”，开发文档中“黑色画布绘制白色矩形”的描述与官方语义一致，但需要统一表述。

官方文档原文：mask 的完全透明区域（即 alpha 为零的地方）指示图像应该被编辑的位置。

所以正确的生成逻辑是：

创建一张全黑的 RGBA 画布（alpha = 255，完全不透明）

在需要编辑的区域绘制白色矩形（并将该区域的 alpha 设为 0，完全透明）

保存为 PNG

“黑色画布绘制白色矩形”描述的是视觉效果，“透明区域重绘”描述的是alpha 语义，两者不矛盾。但开发文档中应该统一为一句明确的话：

Mask 是一张带 alpha 通道的 PNG。编辑区域 alpha=0（完全透明），保留区域 alpha=255（完全不透明）。视觉上表现为黑色背景上的白色矩形，但模型读取的是 alpha 通道。

额外约束： mask 文件必须小于 4MB，且与输入图像尺寸一致。生成 mask 后需要加入尺寸校验和压缩步骤。

三、Pydantic 默认值修正
确认结果：TextBlock、LogoBlock、BatchTask 中的列表字段确实应该用 Field(default_factory=list)。

Pydantic v2 虽然内部会对可变默认值做深拷贝保护，但显式使用 default_factory 是更安全、更明确的做法，也能在版本升级或代码迁移时保持行为一致。

需要修正的字段：

python
from pydantic import BaseModel, Field

class SourceImage(BaseModel):
    text_blocks: list[TextBlock] = Field(default_factory=list)
    logo_blocks: list[LogoBlock] = Field(default_factory=list)

class BatchTask(BaseModel):
    jobs: list["Job"] = Field(default_factory=list)
所有列表类型的字段都统一用 default_factory=list，不要写 = []。

四、文件上传安全细则
确认结果：这部分开发文档中完全缺失，需要补充。以下是可直接写入文档的规则。

4.1 文件类型校验
不能只依赖 UploadFile.content_type，客户端可以伪造。必须用 python-magic 检测文件的真实魔数（magic bytes）。

python
import magic

ALLOWED_MIMES = {"image/png", "image/jpeg", "image/webp"}

def validate_image(file: UploadFile):
    header = file.file.read(2048)
    file.file.seek(0)
    mime = magic.from_buffer(header, mime=True)
    if mime not in ALLOWED_MIMES:
        raise HTTPException(400, f"Unsupported file type: {mime}")
4.2 文件大小限制
单张参考图：不超过 50MB（gpt-image-2.5 的输入图上限）

mask 文件：不超过 4MB（API 硬性限制）

单次上传：最多 16 张（API 支持的最大输入图数量）

FastAPI 中通过 UploadFile 的 max_length 或自定义中间件限制请求体大小。

4.3 路径安全
绝对不要使用客户端提供的文件名保存文件。 必须生成基于 UUID 或内容哈希的文件名。

python
import hashlib, secrets
from pathlib import Path

def safe_filename(original_name: str) -> str:
    ext = Path(original_name).suffix.lower()
    if ext not in {".png", ".jpg", ".jpeg", ".webp"}:
        ext = ".png"
    return f"{hashlib.sha256(secrets.token_bytes(32)).hexdigest()}{ext}"
保存路径必须限制在固定的上传目录内，使用 Path.resolve() 校验最终路径是否在允许的根目录下，防止 ../ 路径遍历攻击。

4.4 文件数量与并发
单次 API 调用最多 16 张输入图

批量任务中同时处理的 API 调用数不超过 3（asyncio.Semaphore）

上传接口本身加简单的速率限制

五、SQLite 表结构与事务处理
确认结果：开发文档只说了“持久化到 SQLite”，没有定义表结构和恢复策略。需要补充以下内容。

5.1 表结构
sql
CREATE TABLE tasks (

5.2 事务策略
SQLite 默认是 serializable 隔离级别。对于任务状态更新，采用显式事务：

python
conn = sqlite3.connect("tasks.db", isolation_level=None)  # 关闭隐式事务

def update_job_status(job_id, new_status, **kwargs):
    conn.execute("BEGIN IMMEDIATE")
    try:
        conn.execute(
            "UPDATE jobs SET status=?, updated_at=? WHERE id=?",
            (new_status, datetime.utcnow().isoformat(), job_id)
        )
        conn.execute("COMMIT")
    except Exception:
        conn.execute("ROLLBACK")
        raise
BEGIN IMMEDIATE 在写入前获取写锁，避免多个 worker 同时写导致的锁冲突。

5.3 服务重启恢复
服务启动时，将所有 status = 'processing' 的 Job 重置为 failed，并记录错误原因 "process restarted"。已在 running 状态的 Task 重新入队，只重新执行 pending 和 failed 的 Job。已 done 的 Job 不重复执行。

参考 TaskStateGuard 的状态收敛思路：任务终态不可改写，重复写入相同终态是幂等的，写入冲突终态会被拒绝。

5.4 幂等性保证
每个 Job 有唯一 ID（{task_id}_{source_id}_{step}_{target_id}）。重试时先查询该 Job 是否已 done，已完成的直接跳过，避免重复扣费。

六、串行 vs 合并编辑策略的明确
确认结果：开发文档中给出了原则性的区分，但缺少量化的成本和质量对比。以下是可写入文档的补充。

6.1 质量衰减的量化参考
有测试发现，在多轮编辑中，重复编辑会逐渐使图像变得更锐利、饱和度更高，并带有更强的合成感。建议每 3-5 轮编辑后，从原始参考图重新开始，而不是在已经编辑了多轮的图上继续叠加。

6.2 成本估算模型
假设单次编辑调用消耗约 1000 输出 token（high 质量档位粗略估计）：

策略	5 张图 × 3 步	API 调用次数	估算成本（输出侧）
串行	5×3	15	~$0.45
合并	5×1	5	~$0.15
合并策略成本约为串行的 1/3，但单次失败的代价更高（需要重新生成整张图而非重跑单步）。

6.3 推荐决策规则
条件	推荐策略
编辑区域完全不重叠（如左上角文字 + 右下角 Logo）	可以合并
编辑涉及同一区域或语义依赖（如换背景 + 调主体颜色）	必须串行
快速试稿阶段（Flare 模型，低成本）	优先合并
最终精修阶段（Sunburst 模型，高成本）	优先串行
需要可追溯、可单步重试	必须串行
6.4 失败恢复策略
串行：单步失败只重试该步，前面的成功步骤结果保留。

合并：单次调用失败后，将合并指令拆解为串行单步，逐条重试，定位失败原因。

七、补充：任务取消与超时机制
开发文档中未定义取消机制，建议补充：

每个 Job 有 cancel_requested 标志位。worker 在每一步操作前检查该标志，如果为真则提前退出。

前端提供“取消任务”按钮，调用 POST /api/task/{task_id}/cancel。

取消后的 Task 状态设为 cancelled，已完成的 Job 保留，未完成的标记为 cancelled。

设置全局超时：单个 Job 超过 120 秒未完成，标记为 failed，错误原因为 "timeout"。
