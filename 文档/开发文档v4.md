## 第一轮讨论：建议方案（待确定，暂不开发）

> 本节保留第一轮讨论记录。与后文“第二轮讨论”不一致的内容，以第二轮明确的规则为准；当前仍处于文档讨论阶段。

建议把项目做成“登录后使用的生图平台”：普通用户先体验，付费用户购买积分或周卡、月卡，超管管理用户、渠道、订单和套餐。沿用现有生图流程，先补齐账号、数据隔离和积分账本，再接支付。

### 1. 用户角色与权限

| 角色 | 可以做什么 |
| --- | --- |
| 普通用户 | 注册登录、领取体验积分、使用生图与拼接、管理自己的素材与任务、购买积分或会员 |
| 会员用户 | 普通用户全部功能，加会员有效期、套餐积分、会员价和更高的任务并发额度 |
| 超管 | 管理全部用户、任务、渠道、公共模板、套餐、订单、积分调整与经营统计 |

会员不建议做成永久角色，而是由会员到期时间判断；到期后回到普通用户。超管权限单独保存，注册接口不能自行指定管理员身份。

渠道地址、密钥、模型配置只给超管看。用户提交任务后由平台自动调度渠道。现有首页统计要拆成“我的使用统计”和“超管经营统计”，不能让普通用户看到全站任务、收入或渠道信息。

### 2. 先提供这几个套餐

以下是建议价格，正式上线前可以在管理后台修改。

| 商品 | 价格 | 积分 | 按全额使用折合单价 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 注册体验 | 免费 | 3 | — | 每个通过验证的账号仅领一次 |
| 小额积分包 | ¥6 | 30 | ¥0.20 / 张 | 无会员身份也能购买 |
| 常用积分包 | ¥18 | 120 | ¥0.15 / 张 | 适合偶尔使用 |

周卡、月卡是“固定积分 + 限时会员权益”，不提供不限量生成，也不默认每日重复赠送。第一版不做自动续费，用户手动购买。

建议第一版购买获得的积分不过期，只有免费赠送积分设置有效期；会员到期后，剩余付费积分仍可使用，但并发等权益恢复普通用户档位。这样用户更容易理解，售后也简单。若后续要做过期套餐积分，必须在购买页明确提示，并分账记录。

### 3. 一积分一张图，扣费怎么做

以“最终输出图片”作为扣费单位：一张图选三种比例就是 3 积分；参考图和输入素材不收费，拼接不收费，OCR 识别不扣生图积分。

1. 提交任务前显示预计生成张数和所需积分，积分不足时禁止提交。
2. 后端创建任务时冻结相应积分，防止同时提交多个任务重复花同一笔积分。
3. 每张最终图片成功后结算 1 积分；取消或最终失败释放该张图冻结的积分。
4. 渠道失败后的自动重试最多 3 轮，用户不重复付积分；所有重试仍失败才退款。
5. 成功图片的下载、重复下载和刷新页面不再扣费。
6. 手动重试失败图是新一轮积分冻结；已经成功的图不能借“重试”重复生成。

现有 OCR 文字编辑会额外调用生图模型，真实成本不止最后一张图的 ¥0.05。为保持“一积分一张图”的承诺，建议第一版普通套餐先关闭这项额外编辑，只保留 OCR 识别。若要保留文字编辑，需要另定高级编辑价格并在提交前展示，不能上线后悄悄加扣。

失败请求也可能被上游扣费，超管必须能看到调用次数、重试次数和实际成本记录；当前项目里的固定 ¥0.05 预估不能作为真实结算依据。

### 4. 注册、登录与体验积分

建议第一版采用邮箱 + 密码注册，通过邮箱验证码后赠送 3 积分，另有登录、退出和找回密码页面。赠送积分可以设为 7 天有效，体验会员生图能力，但并发限制为 1 张。

密码只存安全哈希；登录凭证使用 HttpOnly Cookie，后台接口校验权限。注册、验证码和登录加频率限制，赠送积分由唯一领取记录保证不重复发放。免费体验和付费任务分别限制资源占用，防止体验账号占满渠道。

### 5. 支付与订单

支付渠道优先接一个正规支付服务商的支付宝或微信支付。先创建待支付订单，服务端收到并验证支付回调后发积分、开会员；前端“支付成功”页面本身不能发积分。

同一订单的重复通知只处理一次，积分发放与会员开通放在同一数据库事务里。订单保留购买时的价格与积分快照，后续改套餐不影响旧订单。

退款需要关联订单及积分账本：未使用的积分包可按确定后的退款规则处理；已使用套餐不能直接删除订单或随意清空用户余额。

支付接入需要实际商户账号与服务商资料。资料未准备好时，可以先做超管手动充值并记录操作原因，完成内部试用；正式收款前再接真实支付，不把模拟支付当真实订单。

### 6. 页面与后台

- 未登录：平台介绍、套餐价格、登录、注册、找回密码。
- 用户端：首页展示自己的数据和积分；工作台生图；我的任务；我的素材；积分明细；购买套餐；会员与订单。
- 超管端：经营总览、用户管理、渠道管理、全部任务、套餐与订单、积分调整、公共模板管理。

沿用现在的简洁界面风格。用户端隐藏渠道密钥、上游错误详情等内部信息，只提示任务结果和可执行的操作。

现有素材、生成图、ZIP 下载、OCR 缓存和任务重试接口都需要按所属用户鉴权，不能只给页面加登录就算完成。普通用户即使知道别人的文件 ID，也不能访问别人的图片或任务。

### 7. 数据与技术改造

新增用户、登录会话、验证记录、会员有效期、套餐、订单、积分账户、积分流水、任务积分冻结记录等数据。

积分流水只追加，至少区分赠送、购买、冻结、结算、释放、过期、退款和管理员调整。任务和单张图片关联唯一结算记录，保证断网、进程重启或重复回调都不会重复扣积分。余额修改必须通过账本，管理员操作记录操作者和原因。

原有任务、文件、模板加所属用户；现有数据迁移给初始化超管，不能作为全站公共资源暴露。公共模板由超管维护，用户私有模板互相隔离。

建议付费平台上线前把数据库从 SQLite 迁移到 PostgreSQL，使用事务与行锁处理多用户并发扣费。开发阶段先用现有环境验证流程；生产部署再增加独立任务 worker 和共享渠道限流，避免多个后端进程各自使用一套并发额度。

### 8. 实施顺序与验收

## 第二轮讨论：按你的补充收敛规则

### 1. 会员和积分分开管理

你说得对：**会员是使用权益，积分是生图余额；任何用户可用积分不足时，都不能提交生图任务。** 有会员身份也不能透支积分。

账户分别展示三个信息：会员到期时间、可用积分、冻结积分。冻结积分属于正在生成的任务，不能再次使用。

| 购买行为 | 积分怎么变 | 会员怎么变 |
| --- | --- | --- |
| 普通用户购买积分包 | 支付核实后增加对应积分 | 仍是普通用户 |
| 普通用户购买周卡 | 增加套餐内积分 | 从核实入账时起生效 7 天 |
| 普通用户购买月卡 | 增加套餐内积分 | 从核实入账时起生效 30 天 |
| 会员额外购买积分包 | 在原有余额上累加 | 到期时间不变 |
| 会员再次购买周卡或月卡 | 立即增加套餐内积分 | 在现有未到期时间后追加 7 天或 30 天 |
| 会员已到期后再次购买会员 | 增加套餐内积分，原有付费积分保留 | 从本次核实入账时重新计算有效期 |

例如：买月卡获得 360 积分，生成 350 张后剩 10 积分；再买 ¥18 / 120 积分包，余额变为 130 积分，会员到期时间不变。月卡到期后如果还剩 80 个付费积分，这 80 积分继续可用，只是使用普通用户的并发额度。余额为 0 时必须购买积分包或会员套餐才能继续生成。

第一版周卡和月卡采用同一档会员权益，只是时长、价格和所含积分不同，因此可以直接叠加时长，不涉及升降级折算。会员提前续费不会丢失剩余天数。

建议先不做“会员专享积分包价格”，所有人购买同一种积分包价格一致；优惠已经体现在周卡和月卡所含积分中。否则普通积分包、会员加购、重复购买会员会形成多套价格，不利于初期解释和维护。第一轮表格里“会员价”这一项先不实施。

前面的价格表仍为建议值：周卡 ¥12 / 100 积分、月卡 ¥36 / 360 积分尚未收到明确确认，开发时做成超管可配置套餐，上线前再确定。

### 2. 已确认的积分有效期

按你对第 2 点的同意，确定为：

- 注册赠送 3 积分，发放后 7 天有效，每个验证手机号只领取一次。
- 付费积分不过期，包括积分包和周卡、月卡内购买获得的积分。
- 会员权益到期不清空付费积分，也不自动扣钱续费。
- 扣费优先使用即将到期的赠送积分，再使用付费积分。

需要再补一个边界：赠送积分有效期内提交的任务即使跨过到期时间，冻结仍有效；任务最终失败释放时，如果这笔赠送积分已经过期，就记录释放及过期流水，不重新变成可用积分，也不延长有效期。付费积分失败后正常恢复可用。

### 3. 注册和登录改为手机号方案

第一轮的邮箱注册方案取消，改为下面的流程。

**注册：**填写用户名、密码、确认密码、手机号、短信验证码。验证码验证通过后创建账号并发放体验积分。

用户名和手机号都必须唯一。建议用户名 3–24 位，允许中文、字母、数字和下划线；纯数字用户名不开放，避免与手机号登录冲突。密码建议 8–64 位，不允许后台查看明文。

**登录：**同一个账号输入框，支持“用户名 / 手机号 + 密码”。账号禁用、密码校验与登录频率限制统一处理。注册验证码不是每次密码登录的必填项。

**找回密码：**填写已绑定手机号，获取专用于重置密码的短信验证码；验证后设置新密码，并注销该账号已有登录会话。

验证码按手机号、用途、有效期绑定，注册验证码不能用来重置密码；一次使用后失效，建议 5 分钟有效、60 秒后可重新发送，限制发送次数和错误尝试次数。密码重置接口不直接泄露手机号是否已注册。

短信发送需要接入真实短信服务商，并准备发送资质、签名和模板。开发环境可以使用明确开启的测试发送方式，但测试验证码不能在公网生产接口中返回，也不能以固定万能验证码代替真实验证。现阶段不需要把服务商密钥写进本文档。

### 4. 小范围试验：微信二维码收款 + 人工核实

第一版不接自动支付回调，先展示你提供的收款二维码图片，并建立完整的充值订单记录。**只有管理员核实收款后，系统才增加积分和会员时长。** 用户点击“已付款”或上传付款截图都不能直接到账。

建议流程：

1. 用户选择积分包、周卡或月卡，系统创建待付款订单，保存商品、金额、积分、会员天数等购买快照。
2. 页面展示订单号、应付金额、收款二维码和付款说明；提示用户付款时备注订单号，无法备注时保留微信交易单号供核对。
3. 用户付款后提交付款时间、微信交易单号和可选付款截图，订单变成“待审核”。用户付款后先看到“等待管理员核实”，不能显示“充值成功”。
4. 超管在微信实际收款记录中核对金额、付款时间及交易单号，确认后点击“核实到账”。系统在同一个事务中更新订单、发放积分并追加会员时长。
5. 重复点击确认、刷新页面或重复提交凭证都只入账一次；同一微信交易单号不能核销两个订单。
6. 金额不符或无法匹配时标记“需补充信息”，附管理员说明，用户补充材料；不直接让用户重复付款。

订单状态先采用“待付款、待审核、需补充信息、已入账、已取消”。用户只可取消尚未提交付款凭据的订单；已入账订单不能回退到待审核。取消订单后发现真实收款时，由管理员按原订单补录核实流程，不能把已收款当作未付款直接丢弃。

收款二维码由超管在后台上传和替换，普通用户只能查看当前有效二维码。订单记录付款时展示的二维码版本，便于换码后核对旧订单。以后更换对公收款码可以沿用订单和人工核实流程；只有接入支付服务商的查询/回调接口后，才改成自动核实到账，换一张二维码本身不会实现自动充值。

后台手动调整积分与订单充值分开：订单充值必须对应核实的收款，活动赠送或补偿走“管理员调整”，两者都记录操作者、时间和原因。

付款截图、交易单号仅本人和超管可见；截图按私有文件管理，不能使用公开直链。

先开发：手机号注册与找回密码、用户名或手机号密码登录、用户资源隔离、注册赠送、积分冻结与结算、会员时长、套餐展示、二维码充值订单、超管人工核实和用户积分明细。

## 第三轮讨论：主流在线付款流程

正常的在线充值是：**用户选择商品 → 系统创建订单 → 微信或支付宝收款 → 支付平台通知后端 → 后端验证后自动发积分、开会员 → 页面显示到账。** 这个过程不需要管理员逐单点确认。

### 1. 用户实际看到什么

以购买 ¥36 / 360 积分的月卡为例（价格仍为前面建议值）：

1. 用户登录，选择“月会员”，点击购买。
2. 页面显示商品、应付 ¥36、获得 360 积分及 30 天会员权益。
3. 电脑网页通常展示该笔订单专用的支付二维码；手机端根据打开环境跳转微信或支付宝，或在微信内调起支付。
4. 用户在支付平台确认金额并付款。
5. 页面先显示“正在确认支付结果”，收到服务端到账结果后显示“充值成功”，更新积分和会员到期时间。
6. 用户可以在“我的订单”和“积分明细”查看此次充值记录。

电脑扫码、手机网页、微信内网页是不同支付场景，需要选择支付服务商实际支持的产品。第一版可以只做电脑网页扫码支付，其他场景后续补齐。

### 2. 系统背后怎么处理

| 步骤 | 系统处理 | 为什么需要 |
| --- | --- | --- |
| 创建本地订单 | 后端根据套餐读取价格、积分、会员天数，生成唯一订单号并保存购买快照 | 不信任浏览器传来的金额和积分 |
| 创建支付单 | 后端向支付平台下单，获得支付二维码或调起支付所需参数 | 将真实付款绑定到平台订单 |
| 等待付款 | 前端展示付款入口，并定时查询本项目后端的订单状态 | 用户可以看到付款进度 |
| 接收支付通知 | 支付平台通过异步回调通知后端付款结果 | 用户关掉页面也能到账 |
| 校验付款 | 后端验证签名，并核对商户、订单号、金额、币种和成功状态 | 不能凭截图或前端跳转发积分 |
| 入账 | 在同一个数据库事务内标记订单已入账、写积分流水、增加积分并延长会员 | 保证到账完整、不重复发放 |
| 展示结果 | 前端从后端查询到已入账，再显示成功 | 页面结果与账户余额一致 |

支付通知可能重复、延迟或先后顺序不同，所以同一订单必须只能入账一次。不能采用“收到一次通知就加一次积分”的逻辑。

如果回调没有及时到达，后端会主动向支付平台查询订单，查询确认成功后走同一套入账逻辑。定期对账再核查本地订单和支付记录，处理漏单等异常。

### 3. 个人微信收款码和商户支付二维码的区别

| 对比项 | 现在计划用的个人收款码 | 正式商户支付 |
| --- | --- | --- |
| 二维码 | 一张收款码，多个用户共用 | 电脑扫码场景通常按订单生成专用支付码 |
| 金额 | 用户可能需要自己输入 | 系统下单时确定，支付页面展示 |
| 对应订单 | 依靠备注、时间、金额和交易记录人工匹配 | 支付平台交易直接关联商户订单号 |
| 到账确认 | 超管查看实际收款后人工核实 | 服务端验签并核对订单，自动确认 |
| 积分到账 | 人工确认后到账 | 支付确认后自动到账 |
| 退款与对账 | 主要靠人工处理 | 可通过服务商接口处理并留存记录 |

**把个人收款码截图放进网页，不等于接入微信支付。换成对公账户的静态收款码，也不会自动具备订单回调能力。** 自动到账需要正式接入支持商户下单、交易查询和支付通知的接口。

### 4. 正式接入通常需要准备什么

- 选择微信支付、支付宝的直接商户接入，或能够提供正规支付接口的服务商。
- 按选定支付产品完成商户入驻、身份或经营主体审核、结算账户配置；具体支持的主体和材料以服务商要求为准，不能默认私人二维码就能调用商户 API。
- 准备平台部署域名、HTTPS 和可从公网访问的后端支付通知地址；备案、应用配置等按所选支付产品要求办理。
- 在服务端配置商户号、应用标识、证书或密钥等资料，密钥不放到前端，也不写进本文档。
- 准备商品说明、订单查询入口、客服和退款规则，然后按服务商要求联调、验收。

正式商户收款可按配置的结算规则进入绑定账户，支付成功通知与资金结算到银行卡不是同一个时间点。用户积分以核实的支付成功结果入账，不必等待银行结算完成。

### 5. 放到本项目里怎么安排

你现在是小范围试验，仍可以先用“二维码展示 + 管理员核实”，但从第一版就建立订单、套餐快照、唯一入账记录和积分账本。收款确认和积分入账分开设计：

- 试验阶段：管理员核实真实收款，触发统一入账流程。
- 正式支付阶段：支付回调验签或主动查单成功，触发同一个入账流程。

这样后续主要替换支付下单与收款确认方式，用户余额、积分结算、会员续期规则继续沿用。

后续正式支付建议先接一种支付方式，跑通下单、支付、补单、退款和对账，再增加第二种。当前继续保留人工收款试验方案，不因为本轮解释就自动改为开发正式支付。
