## 一、项目概述

### 1.1 项目名称

`ecom-image-studio`

### 1.2 项目目标

构建一个前后端分离的电商图片批量处理工作台，支持以下两条核心工作流：

**工作流 A：5 张参考图 → 5 张成品图**

用户上传最多 5 张参考底图。系统识别文字块和 Logo 块，用户逐块指定修改内容，后端通过图像编辑模型生成对应成品图。每张参考图独立处理，允许使用统一编辑规则，也允许对单张图覆盖配置。

**工作流 B：5 张成品图 → 1 张电商长图**

用户按照指定顺序将成品图纵向拼接成详情页长图，支持输出宽度、图片间距、背景色、顶部留白和底部留白。

### 1.3 核心约束

- 每个文字块必须独立识别、独立编号、独立配置、独立生成 Mask 和独立编辑。
- 每个 Logo 块必须独立识别或手动框选，并可独立替换。
- 默认采用单步串行编辑，保证可追溯、可重试和较高的局部编辑稳定性。
- 所有模型调用必须保存完整输入快照，确保任务可审计。
- 所有用户上传文件必须经过真实类型、大小、尺寸和路径安全校验。
- 取消任务不能立即制造状态不一致；任务最终状态必须在 Job 收敛后确定。
- 后端不能写死任何具体中转站地址，必须通过环境变量配置。

## 三、外部 API 接入规范

### 3.1 接入方式

本项目通过 OpenAI 兼容中转站调用图像编辑模型。后端使用异步 SDK：

```python
from openai import AsyncOpenAI

client = AsyncOpenAI(
    api_key=settings.openai_api_key,
    base_url=settings.openai_base_url,
    timeout=settings.request_timeout,
)
```

不得使用同步的 `OpenAI` 客户端包裹在 `asyncio.to_thread()` 中作为主实现。原因是线程无法可靠地被任务取消强制终止，无法满足 Job 超时和取消语义。

### 3.2 环境变量

```bash
OPENAI_API_KEY=your_token
OPENAI_BASE_URL=https://your-relay.example/v1
MODEL_EDIT=gpt-image-2.5-sunburst
MODEL_DRAFT=gpt-image-2.5-flare
MAX_CONCURRENCY=3
REQUEST_TIMEOUT=60
JOB_TIMEOUT=240
MAX_RETRIES=2
DATA_DIR=./backend/media
DATABASE_PATH=./backend/data/tasks.db
FRONTEND_ORIGINS=http://localhost:5173
```

规则：

- `OPENAI_API_KEY` 必填，禁止写入代码、日志和数据库。
- `OPENAI_BASE_URL` 必填，不提供默认值；缺失时后端启动失败。
- `MODEL_EDIT` 和 `MODEL_DRAFT` 是候选模型 ID，不代表一定会被实际使用。
- `MAX_CONCURRENCY` 默认 3，必须限制在 1 至 3 之间。
- `REQUEST_TIMEOUT` 是单次 HTTP 请求超时，默认 60 秒。
- `JOB_TIMEOUT` 是整个 Job 超时，默认 240 秒。
- `MAX_RETRIES=2` 表示首次调用之外最多重试 2 次。
- 项目根目录的 `.gitignore` 必须包含 `.env`、`*.key`、`secrets/`、`backend/media/` 和数据库文件。

### 3.3 图像编辑接口

后端通过兼容接口调用图像编辑能力，逻辑上对应：

```text
POST /v1/images/edits
Content-Type: multipart/form-data
```

主要参数：

| 参数 | 说明 |
|---|---|
| `model` | 启动时解析出的编辑模型 ID |
| `image` | 单张输入图片；每次编辑默认只传一张 |
| `mask` | 与输入图尺寸一致的 RGBA PNG |
| `prompt` | 编辑指令 |
| `size` | `1024x1024`、`1536x1024`、`1024x1536` 或 `auto` |
| `quality` | `low`、`medium`、`high`、`xhigh`、`max` 或 `auto`，以中转站支持情况为准 |
| `output_format` | `png`、`jpeg` 或 `webp` |
| `n` | 默认 1 |
| `input_fidelity` | 能力可用时才传，默认 `high` |

重要规则：

- 每次 API 调用默认只处理一张图。
- 并发中的模型请求数不超过 `MAX_CONCURRENCY`。
- API 返回的 Base64 图片必须立即落盘，不能只保存在内存中。
- 每次调用必须保存原图哈希、Mask 哈希、Prompt、模型、参数、开始时间、结束时间和响应元数据。
- 如果参数被中转站拒绝，只对明确的“不支持参数”错误做参数降级，不得对所有异常盲目重试。

### 3.4 启动时模型列表校验

后端启动时调用兼容站点的模型列表接口，逻辑上对应 `GET /v1/models`。

**模型列表请求失败：**

- 记录明确错误。
- 进程退出，不启动一个必然无法工作的服务。

**模型解析顺序：**

1. 精确匹配 `MODEL_EDIT` 或 `MODEL_DRAFT`。
2. 对模型 ID 做大小写不敏感的完整字符串匹配。
3. 如果仍未找到，仅筛选包含 `gpt-image-2.5` 的候选。
4. 只有一个候选时，警告后使用该候选。
5. 有多个候选时不自动猜测，标记该角色不可用，并要求用户显式配置模型 ID。
6. 没有候选时标记该角色不可用。

第一阶段只要求编辑模型可用；草稿模型不可用时服务可以以 `degraded` 状态启动。

健康检查应返回：

```json
{
  "status": "ok",
  "models": {
    "edit": {
      "configured": "gpt-image-2.5-sunburst",
      "resolved": "gpt-image-2.5-sunburst",
      "available": true
    },
    "draft": {
      "configured": "gpt-image-2.5-flare",
      "resolved": null,
      "available": false
    }
  },
  "capabilities": {
    "input_fidelity": "unknown",
    "background": "unknown",
    "output_compression": "unknown",
    "stream": "unknown"
  }
}
```

当编辑模型不可用时，`status` 必须为 `degraded`，生成接口返回明确的不可用错误。

### 3.5 能力探测和降级

启动阶段不得默认发送收费的测试图片请求。能力状态采用以下策略：

- 若中转站的模型列表或扩展信息明确提供能力声明，则读取声明。
- 若没有能力声明，状态记为 `unknown`，核心请求先不发送可选参数或使用保守参数。
- 如果真实请求返回明确的“不支持参数”错误，则记录该模型/中转站能力为 `unsupported`，移除对应可选参数后重试一次。
- 如果是网络、鉴权、限流或服务端错误，不得误判为“不支持参数”。
- 能力探测失败只影响可选能力，不影响后端启动。

支持状态统一为 `true`、`false` 或 `unknown`，便于健康检查和日志排查。

## 四、核心概念与数据模型

| 概念 | 说明 |
|---|---|
| Source | 用户上传的参考底图 |
| Output | 编辑后的成品图 |
| Composite | 拼接后的长图 |
| TextBlock | OCR 检测到的一处文字块 |
| LogoBlock | 检测到或手动框选的一处 Logo |
| Mask | 指示模型可重绘区域的 RGBA PNG |
| EditStep | 一次背景、颜色、组件、文字或 Logo 编辑 |
| Task | 一次批量任务 |
| Job | 一个 Source 的一个编辑步骤 |

### 4.1 Pydantic 模型

所有列表字段必须使用 `Field(default_factory=list)`，禁止写 `= []`。

```python
from datetime import datetime
from pydantic import BaseModel, Field

class TextBlock(BaseModel):
    id: str
    bbox: tuple[int, int, int, int]
    position: str
    original: str
    replace: str = ""
    enabled: bool = True
    mask_path: str | None = None

class LogoBlock(BaseModel):
    id: str
    bbox: tuple[int, int, int, int]
    position: str
    detected: bool = True
    replace_with: str | None = None
    enabled: bool = True
    mask_path: str | None = None

class SourceImage(BaseModel):
    id: str
    filename: str
    path: str
    width: int
    height: int
    text_blocks: list[TextBlock] = Field(default_factory=list)
    logo_blocks: list[LogoBlock] = Field(default_factory=list)

class EditRule(BaseModel):
    text_replace_enabled: bool = True
    logo_replace_enabled: bool = True
    background_replace_enabled: bool = False
    background_prompt: str = ""
    shade_color_enabled: bool = False
    shade_color: str = ""
    bulb_replace_enabled: bool = False
    bulb_prompt: str = ""
    quality: str = "high"
    size: str = "1024x1024"
    output_format: str = "png"
    strategy: str = "serial"

class BatchTask(BaseModel):
    id: str
    created_at: datetime
    source_ids: list[str] = Field(default_factory=list)
    edit_rule: EditRule
    status: str
    jobs: list["Job"] = Field(default_factory=list)

class Job(BaseModel):
    id: str
    task_id: str
    source_id: str
    step: str
    target_id: str | None = None
    status: str = "pending"
    prompt: str = ""
    mask_path: str | None = None
    input_path: str = ""
    output_path: str = ""
    error: str | None = None
    retry_count: int = 0
    cancel_requested: bool = False
```

### 4.2 Job ID 和幂等

Job ID 由以下内容组成并保证唯一：

```text
{task_id}_{source_id}_{step}_{target_id_or_none}
```

重试前必须先查询 Job：

- `done`：直接返回已有结果，不重新扣费。
- `cancelled`：只有用户明确创建新任务或显式恢复时才允许重新执行。
- `failed`：允许增加 `retry_count` 后重试，最多 `MAX_RETRIES` 次。
- `processing`：不得重复启动；由恢复逻辑或原 worker 负责收敛。

## 五、Mask 规范

### 5.1 Alpha 语义

Mask 是一张与输入图尺寸完全一致的 RGBA PNG：

- 编辑区域：`alpha=0`，完全透明，模型允许重绘。
- 保留区域：`alpha=255`，完全不透明，模型应保持不变。
- RGB 颜色只用于视觉调试，模型读取的是 Alpha 通道。
- 视觉上可以表现为黑色背景上的白色矩形，但必须保证编辑区域的 Alpha 为 0。

### 5.2 Mask 生成

```python
from PIL import Image, ImageDraw

def make_rect_mask(width: int, height: int, bbox: tuple[int, int, int, int]) -> Image.Image:
    mask = Image.new("RGBA", (width, height), (0, 0, 0, 255))
    draw = ImageDraw.Draw(mask)
    x1, y1, x2, y2 = bbox
    draw.rectangle((x1, y1, x2, y2), fill=(255, 255, 255, 0))
    return mask
```

实际实现必须先裁剪和校验坐标：

- `0 <= x1 < x2 <= width`
- `0 <= y1 < y2 <= height`
- 越界请求返回 `422`，不自动静默扩大区域。
- OCR 生成的框可向外扩展 5 至 8 像素，但扩展后必须再次裁剪到图片边界。
- 生成后校验尺寸、RGBA 模式、PNG 格式和文件大小。
- Mask 文件不超过 4 MB。
- 文件过大时使用无损 PNG 优化；优化后仍超限则返回明确错误。

### 5.3 多文字块原则

一处文字 = 一个唯一 ID = 一个独立 Mask = 一次独立编辑。

位置由 bbox 中心点映射到九宫格：

```python
def bbox_to_position(bbox, img_w, img_h):
    x1, y1, x2, y2 = bbox
    cx = (x1 + x2) / 2 / img_w
    cy = (y1 + y2) / 2 / img_h
    col = "left" if cx < 0.33 else "right" if cx > 0.67 else "center"
    row = "top" if cy < 0.33 else "bottom" if cy > 0.67 else "middle"
    return f"{row}-{col}" if (row, col) != ("middle", "center") else "center"
```

默认不合并重复原文的多个区域。若用户明确要求同时替换，才创建合并 Mask，并在 Prompt 中写明 `all instances`。

## 六、编辑类型和 Prompt 规范

Prompt 必须由 `prompt_builder.py` 模板化生成，不能在路由函数中散落硬编码。通用结构为：

```text
[具体改动] + [必须保留的内容] + [输出格式约束]
```

### 6.1 背景替换

```text
Replace only the background with {background_description}.
Keep the {subject} completely unchanged — its shape, proportions, color,
material, metal finish, cable, contact shadows, and all existing text and logo.
Preserve the original composition, camera angle, and product position.
Do not alter any part of the {subject}.
Output a photorealistic e-commerce product image.
```

### 6.2 主体局部换色

```text
Change only the {target} color to {color}.
Keep its shape, material texture, seams, stitching, frame, bulb, cable,
background, and all text and logo exactly the same.
Preserve the original lighting, shadows, and perspective.
Do not alter anything else.
Output a photorealistic product image.
```

### 6.3 局部组件替换

```text
Replace only the {target} with {description}.
Match the original socket position, scale, perspective, and lighting.
Keep the surrounding product, cable, background, and all text and logo
completely unchanged.
Do not alter anything else.
Output a photorealistic product image.
```

### 6.4 文字替换

```text
Replace the text "{original}" located in the {position} area with "{replace}".
Match the original font style, weight, color, size, perspective, and shadow exactly.
The new text must be perfectly spelled and aligned.
Do not alter any other text, graphics, the product, or the background.
Output a photorealistic e-commerce product image.
```

如果 `original == replace`、`replace` 为空或该块未启用，后端不创建 Job、不调用 API。

### 6.5 Logo 替换

Logo 替换时，原图作为 Image 1，自有 Logo 文件作为 Image 2；若中转站不支持多图输入，必须使用预合成参考图或明确返回“不支持 Logo 替换”。

```text
Remove the existing logo in the {position} area.
Replace it with the logo from Image 2: the {brand} wordmark.
Scale it to fit the same bounding box, maintain its original aspect ratio,
and preserve the background texture and lighting in that area.
Do not change anything else in the image.
Output a photorealistic e-commerce product image.
```

## 七、编辑策略、重试和质量控制

### 7.1 串行策略

默认 `strategy=serial`：

1. 以原图作为第一步输入。
2. 每次只编辑一个区域或一个逻辑步骤。
3. 上一步输出作为下一步输入。
4. 每一步保存独立输入快照和输出文件。
5. 单步失败只重试该步，前面的成功结果保留。

### 7.2 合并策略

以下情况可以合并：

- 编辑区域完全不重叠。
- 多张图执行完全相同的单一编辑。
- 快速试稿阶段使用草稿模型。

以下情况必须串行：

- 编辑区域重叠。
- 存在光影、主体或背景语义依赖。
- 需要逐步审计、单步重试或最终精修。

合并请求失败时，系统拆解为串行 Job 逐条执行，不直接丢失整个任务。

### 7.3 重试规则

- 默认最多重试 2 次。
- 网络错误、限流、临时服务端错误和明确的可降级参数错误可重试。
- 参数校验、文件损坏、模型不可用、用户取消和不可恢复错误不得盲目重试。
- 每次重试递增 `retry_count`，写入错误原因和时间。
- 重试不能覆盖已有成功输出。

### 7.4 超时规则

采用两层超时，且数值保持一致：

| 层级 | 配置 | 默认值 | 范围 | 行为 |
|---|---|---:|---|---|
| SDK | `REQUEST_TIMEOUT` | 60 秒 | 单次 HTTP 请求 | 抛出超时异常，按重试规则处理 |
| Job | `JOB_TIMEOUT` | 240 秒 | Job 全流程 | 取消内部协程，Job 标记 `failed`，错误为 `job_timeout` |

默认最多 2 次重试，即最多 3 次请求。Job 超时必须覆盖请求、退避、Mask 处理和持久化的总耗时；如果部署环境需要更长请求时间，必须同步提高 `JOB_TIMEOUT`。

### 7.5 并发

- 使用 `asyncio.Semaphore(MAX_CONCURRENCY)`。
- 默认最大并发为 3。
- 并发限制作用于实际模型 API 调用，不是只限制任务创建。
- 单个任务内的同一 Source 默认按步骤串行。
- 不同 Source 的 Job 可以并发。

## 八、任务状态、取消和恢复

### 8.1 Task 状态机

```text
queued    → running | cancelled
running   → completed | partial_failed | failed | cancelling
cancelling → cancelled | completed | partial_failed | failed
cancelled → 终态
completed → 终态
partial_failed → 终态
failed → 终态
```

取消请求不是立即写入 `cancelled` 终态，而是先进入 `cancelling`，等待所有 Job 收敛后再计算最终状态。这样避免 Task 已是终态但 Job 仍处于 `processing` 的竞态。

### 8.2 Job 状态机

```text
pending    → processing | cancelled
processing → done | failed | cancelled
failed     → processing | failed
cancelled  → 终态
done       → 终态
```

### 8.3 取消语义

`POST /api/task/{task_id}/cancel` 的处理：

1. 在事务中把所有 `pending` 和 `processing` Job 的 `cancel_requested` 设为 1。
2. Task 从 `queued` 或 `running` 改为 `cancelling`。
3. 已经 `done` 的 Job 不变。
4. 已经 `failed` 的 Job 不变，除非它当前正在被重试。
5. Worker 在开始执行前、每次 API 调用前、每次 API 调用返回后检查取消标志。
6. 检查到取消后，若 API 已返回则丢弃结果，不写入 output；Job 标记为 `cancelled`。
7. 所有 Job 进入终态后，Task 才写入 `cancelled`；若取消时所有工作已完成，则按实际结果写入 `completed` 或 `partial_failed`。

对于正在进行的 HTTP 请求，使用 `AsyncOpenAI` 的异步请求任务；取消协程后关闭或释放请求资源。不能保证远端已经收到的请求被服务商撤回，因此取消后必须丢弃返回结果，不得将其视为成功输出。

### 8.4 服务重启恢复

服务启动时：

- 所有 `processing` Job 重置为 `failed`，错误为 `process_restarted`。
- `running` 或 `cancelling` Task 重新计算状态。
- 仅重新执行 `pending` 和符合重试条件的 `failed` Job。
- `done`、`cancelled` 不得重复执行。
- 任务终态不可被普通更新覆盖；重复写入相同终态必须幂等，写入冲突终态必须拒绝。

## 九、SQLite 数据库

### 9.1 表结构

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id TEXT PRIMARY KEY,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    source_ids TEXT NOT NULL,
    edit_rule TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'queued',
    error TEXT
);

CREATE TABLE IF NOT EXISTS jobs (
    id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL,
    source_id TEXT NOT NULL,
    step TEXT NOT NULL,
    target_id TEXT,
    status TEXT NOT NULL DEFAULT 'pending',
    prompt TEXT NOT NULL DEFAULT '',
    mask_path TEXT,
    input_path TEXT NOT NULL DEFAULT '',
    output_path TEXT NOT NULL DEFAULT '',
    error TEXT,
    retry_count INTEGER NOT NULL DEFAULT 0,
    cancel_requested INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY (task_id) REFERENCES tasks(id)
);

CREATE INDEX IF NOT EXISTS idx_jobs_task_id ON jobs(task_id);
CREATE INDEX IF NOT EXISTS idx_jobs_status ON jobs(status);
CREATE INDEX IF NOT EXISTS idx_jobs_cancel ON jobs(cancel_requested)
WHERE cancel_requested = 1;
```

任务和 Job 的完整输入快照可以存放在 `snapshots/` 目录，数据库中只保留快照路径和关键索引字段。

### 9.2 事务

状态更新必须使用显式事务。写入冲突时必须回滚并记录日志：

```python
conn = sqlite3.connect(db_path, isolation_level=None)
conn.execute("BEGIN IMMEDIATE")
try:
    # 校验当前状态后更新
    conn.execute("COMMIT")
except Exception:
    conn.execute("ROLLBACK")
    raise
```

数据库连接不得在多个异步任务间无保护共享；可以使用单写连接、线程锁或异步数据库访问层，但必须保证状态更新串行化。

## 十、文件上传与存储安全

### 10.1 文件类型

允许输入：`png`、`jpg`、`jpeg`、`webp`。不能只信任 `UploadFile.content_type`，必须使用 `python-magic` 检查真实魔数，并使用 Pillow 验证文件可解码。

### 10.2 限制

- 单个源图片不超过 50 MB。
- Mask 不超过 4 MB。
- 单次上传最多 16 张图；工作流默认最多 5 张。
- 限制请求体大小，避免超大请求在应用层之前耗尽内存。
- 对上传接口增加简单速率限制。

### 10.3 文件名和路径

- 禁止使用客户端原始文件名作为落盘文件名。
- 使用 UUID 或内容哈希生成文件名，保留经过白名单过滤的扩展名。
- 所有文件必须存放在固定 `DATA_DIR` 下的 `source/`、`output/`、`masks/`、`composite/` 或 `snapshots/` 子目录。
- 使用 `Path.resolve()` 检查最终路径确实位于允许根目录内，防止 `../` 路径遍历。
- API 返回逻辑 `file_id`，不直接暴露任意本地路径。

```http
POST /api/generate/batch
```

请求核心结构：

```json
{

    "logo_replace_enabled": true,
    "background_replace_enabled": false,

        {"id": "T1", "replace": "新品首发", "enabled": true}
      ]
    }
  }
}
```

返回：

```json
{"task_id": "task_...", "status": "queued", "total_jobs": 6}
```

### 11.5 第一阶段单 Job 创建

```http
POST /api/task/create
```

第一阶段参数：

```json
{
  "file_id": "src_1",

  "prompt": "Replace the text ...",
  "size": "1024x1024",
  "quality": "high",
  "output_format": "png"
}
```

坐标采用左上角原点的绝对像素坐标 `[x1, y1, x2, y2]` 语义；后端负责校验，越界返回 `422`。后端根据输入图尺寸生成 Mask。

### 11.6 任务查询

```http
GET /api/task/{task_id}
```

返回 Task、Job 状态、进度、错误、输入输出 URL 和快照信息。

```http
POST /api/task/{task_id}/cancel
```

取消请求返回：

```json
{
  "task_id": "task_1",
  "status": "cancelling",
  "cancel_requested_jobs": 3,
  "already_done_jobs": 2
}
```

接口幂等：任务已取消时返回当前状态；任务已完成时不改变结果。

### 11.8 任务进度流

```http
GET /api/task/{task_id}/stream
```

优先使用 SSE。若部署环境不支持 SSE，前端每 3 秒轮询任务查询接口。

### 11.9 重试和编辑

```http
POST /api/task/{task_id}/retry
POST /api/task/{task_id}/job/{job_id}/edit
```

支持按 Job 重试、按 Source 重试和修改 Prompt 后重新执行。已完成 Job 默认不覆盖原输出，修改后创建新的编辑版本或新的 Job ID。

### 11.10 文件下载

```http
GET /api/files/{file_id}
```

只允许访问数据库中已登记的文件 ID，不接受任意路径参数。

### 11.11 长图拼接

```http
POST /api/composite
```

请求：

```json
{
  "image_ids": ["out_1", "out_2", "out_3"],
  "width": 750,
  "gap": 0,
  "background_color": "#FFFFFF",
  "padding_top": 0,
  "padding_bottom": 0,
  "output_format": "png"
}
```

Pillow 负责按顺序缩放、居中、填充和拼接，返回长图 `file_id` 和下载 URL。

### 11.12 历史任务

```http
GET /api/tasks
```

支持按状态、时间和分页查询历史任务。

## 十四、分阶段开发计划

每个阶段完成后先运行验证，再进入下一阶段。除非用户明确要求连续实现，否则完成一个阶段后停止并报告结果。

### 第一阶段：后端骨架和单图编辑

目标：跑通“上传一张图 → 手工矩形 Mask → 异步图像编辑 → 保存输出”。

实现：

- FastAPI 应用、配置读取和日志。
- `AsyncOpenAI` 初始化。
- 启动时模型列表获取和模型解析。
- `GET /api/health`。
- 文件上传和安全校验。
- SQLite `tasks`、`jobs` 表。
- `/api/task/create`、任务查询、文件下载。
- 绝对像素矩形 Mask。
- `REQUEST_TIMEOUT=60`、`JOB_TIMEOUT=240`、最多 2 次重试。
- 取消标记、取消检查点和 `cancelling` 收敛状态。

不做：OCR、多文字块、Logo、前端、批量并发、长图拼接。

验收：

1. 使用 curl 上传一张测试图。
2. 创建矩形编辑任务。
3. 查询任务直到 `completed`。
4. 下载并检查输出图片。
5. 检查 SQLite 中 Task、Job 和快照记录。
6. 另一次测试中请求取消，确认最终 Task 和 Job 都为 `cancelled`。
7. 使用不可用模型配置，确认服务以 `degraded` 启动且生成接口给出清晰错误。

### 第二阶段：OCR 和多文字块

- 接入 PaddleOCR。
- 返回 TextBlock、bbox、位置和原文。
- 为每个文字块生成独立 Mask。
- 支持原图标注所需的缩略图和坐标信息。

验收：至少一张包含 3 个文字块的图片能正确返回 `T1` 至 `T3` 和独立 Mask。

### 第三阶段：批量任务

- 实现 `POST /api/generate/batch`。
- 5 张图并发处理，实际模型调用并发不超过 3。
- 每张图内部按文字块顺序串行。
- 实现任务查询、SSE 或轮询、失败重试和服务重启恢复。

### 第四阶段：Prompt 模板化

- 实现五类编辑模板。
- Prompt 必须包含目标位置和原文字引用。
- 增加 Prompt 快照和预览。
- 增加策略校验，避免不符合条件的合并编辑。

### 第五阶段：Logo、背景和主体编辑

- 支持 Logo 上传和替换。
- 使用 rembg 生成背景编辑区域。
- 支持主体局部框选和局部描述。
- 完善能力不可用时的降级提示。

### 第六阶段：长图拼接

- 实现 `/api/composite`。
- 支持排序、宽度、间距、背景色、顶部和底部留白。
- 对不同宽高比图片进行等比缩放和居中。

### 第七阶段：前端工作台

- React、Vite、Ant Design 基础工程。
- 上传、标注、文字块表格、规则配置和提交任务。
- 前端代理、CORS 和错误提示。

### 第八阶段：任务详情与联调

- 实时进度、结果对比、单步重试、Prompt 微调。
- 长图拼接编辑器。
- 任务历史页、SSE、端到端测试。
- 性能、日志、异常和部署优化。

## 十九、最终开发原则

1. 先保证状态、文件和快照可追溯，再追求批量速度。
2. 先用 Mock 或单图闭环验证基础设施，再接入 OCR 和复杂编辑。
3. 任何新参数都必须有配置、校验、降级和日志策略。
4. 任何 Job 都必须可查询、可重试、可取消或明确说明不可取消原因。
5. 不因模型返回偶发成功而跳过输入校验、权限提示和数据持久化。
6. 每完成一个阶段都必须有可重复的验收命令和明确的停止点。
