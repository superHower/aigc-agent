## 一、cancel_requested 加入 jobs 表

**决策**：作为 jobs 表的一等字段，而不是放在 JSON 里。

```sql
ALTER TABLE jobs ADD COLUMN cancel_requested INTEGER NOT NULL DEFAULT 0;
CREATE INDEX idx_jobs_cancel ON jobs(cancel_requested) WHERE cancel_requested = 1;
```

语义：

- `0` = 未请求取消
- `1` = 已请求取消，worker 在下一个检查点退出

worker 在每个 Job 的以下位置检查 `cancel_requested`：

1. 开始执行前
2. 每次 API 调用前
3. 每次 API 调用返回后（拿到结果也丢弃，不写入 output）

检查到 `1` 时，把 Job 状态置为 `cancelled`，写入 `updated_at`，不再执行后续步骤。

## 二、取消接口与状态机

**决策**：新增路由 `POST /api/task/{task_id}/cancel`，任务级取消。

### 接口定义

```http
POST /api/task/{task_id}/cancel
Response 200:
{
  "task_id": "...",
  "cancelled_jobs": 3,
  "already_done_jobs": 12,
  "status": "cancelled"
}
```

### 状态机更新

新增两个终态：`cancelled`（任务级）和 `cancelled`（Job 级）。

**任务状态转移**：

```
queued    → running | cancelled
running   → completed | partial_failed | failed | cancelled
cancelled → (终态，不可再转移)
completed | partial_failed | failed → (终态)
```

**Job 状态转移**：

```
pending    → processing | cancelled
processing → done | failed | cancelled
cancelled  → (终态)
done | failed → (终态，不可再转移)
```

### 取消语义

- 任务级取消：把所有 `pending` 和 `processing` 的 Job 的 `cancel_requested` 置为 1。
- 已经 `done` 的 Job 不动。
- 已经 `failed` 的 Job 不动。
- 任务状态立即置为 `cancelled`，但 worker 会异步把正在执行的 Job 收敛到 `cancelled`。
- 前端收到 `cancelled` 后停止轮询。

## 三、120 秒超时的精确定义

**决策**：**两层超时都要设**，语义不同，互不替代。

| 层级 | 名称 | 默认值 | 范围 | 触发后的行为 |
|------|------|--------|------|-------------|
| SDK 层 | `REQUEST_TIMEOUT` | 180 秒 | 单次 HTTP 请求 | 抛出 `openai.APITimeoutError`，进入重试逻辑 |
| Job 层 | `JOB_TIMEOUT` | 120 秒 | 单个 Job 全流程 | 强制终止 Job，状态置 `failed`，错误原因 `"job_timeout"` |

**为什么 SDK 超时反而更长？**  
SDK 层超时是防止单次 HTTP 请求永久挂起。Job 层超时是防止一个 Job 因为重试、mask 生成、OCR 等环节累积超时。所以 Job 层必须比 SDK 层短，才能在 SDK 还没超时之前就放弃整个 Job。

**实现方式**：

```python
import asyncio

async def run_job(job):
    try:
        await asyncio.wait_for(_run_job_inner(job), timeout=JOB_TIMEOUT)
    except asyncio.TimeoutError:
        job.status = "failed"
        job.error = "job_timeout"
        save_job(job)
```

`_run_job_inner` 内部的每次 SDK 调用有自己的 `timeout=REQUEST_TIMEOUT`。

**两者的关系**：一个 Job 最多重试 2 次，每次 SDK 超时 180 秒。如果两次都 SDK 超时，Job 层 120 秒早就触发了，所以实际效果是 Job 层超时先生效。这两个值需要配合，不要出现 SDK 超时比 Job 超时还长的情况。

## 四、启动时的模型与能力探测策略

**决策**：分两类，处理方式不同。

### 模型列表（`GET /v1/models`）失败

**启动失败**，进程退出，日志输出明确错误。

理由：如果连模型列表都拿不到，说明中转站配置、密钥、网络任一环节有问题。这种情况下后端跑起来也无法处理任何请求，不如直接失败，让人立刻发现。

```python
try:
    models = client.models.list()
except Exception as e:
    logger.error(f"Failed to list models from relay: {e}")
    raise SystemExit(1)
```

### 模型 ID 校验

**警告后启动**，但把该模型标记为不可用。

理由：用户可能配置了多个模型，其中某个不在列表里。不应该因为一个模型缺失就让整个服务挂掉。

```python
available = {m.id for m in models.data}
for role, model_id in [("edit", MODEL_EDIT), ("draft", MODEL_DRAFT)]:
    if model_id not in available:
        logger.warning(f"Model '{model_id}' not found in relay. "
                       f"Role '{role}' will be unavailable until fixed.")
        capabilities[role] = False
```

启动后，`GET /api/health` 返回中标注哪些模型可用：

```json
{
  "status": "degraded",
  "models": {"edit": true, "draft": false},
  "capabilities": {"input_fidelity": true, "background": false}
}
```

### 能力探测失败

**自动降级，警告后启动。**

理由：`input_fidelity`、`background`、`stream` 这些是可选优化参数，不支持也不影响核心功能。探测失败时把对应能力置为 `false`，后续调用不传这个参数即可。

```python
capabilities = {
    "input_fidelity": probe_input_fidelity(client),
    "background": probe_background(client),
    "output_compression": probe_output_compression(client),
    "stream": probe_stream(client),
}
```

探测本身用最小请求（比如一张 64×64 的测试图），成本可忽略。探测失败不抛异常，只是把对应项置 `false`。

## 六、模型 ID 以启动时 `/v1/models` 返回为准

**决策**：环境变量 `MODEL_EDIT` 和 `MODEL_DRAFT` 只是**候选值**，实际使用前必须经过 `/v1/models` 校验。

### 校验流程

```python
def resolve_model(client, env_value, role, available_ids):
    if env_value in available_ids:
        return env_value
    # 尝试模糊匹配（例如中转站把 gpt-image-2.5-sunburst 写成 gpt-image-2.5-sb）
    candidates = [m for m in available_ids if "gpt-image-2.5" in m]
    if len(candidates) == 1:
        logger.warning(f"Model '{env_value}' not found. "
                       f"Using '{candidates[0]}' for role '{role}'.")
        return candidates[0]
    if not candidates:
        logger.warning(f"No gpt-image-2.5 model found for role '{role}'.")
        return None
    logger.warning(f"Multiple candidates for role '{role}': {candidates}. "
                   f"Using '{candidates[0]}'. Please set MODEL_{role.upper()} explicitly.")
    return candidates[0]
```

### 规则

1. 精确匹配 → 直接使用。
2. 找不到，但有唯一 `gpt-image-2.5-*` 候选 → 警告后使用该候选。
3. 有多个候选 → 警告后使用第一个，提示用户显式配置。
4. 完全找不到 → 该 role 标记不可用，服务以 `degraded` 状态启动。

### 健康检查输出

```json
{
  "status": "degraded",
  "models": {
    "edit": {"configured": "gpt-image-2.5-sunburst", "resolved": "gpt-image-2.5-sunburst", "available": true},
    "draft": {"configured": "gpt-image-2.5-flare", "resolved": null, "available": false}
  }
}
```
